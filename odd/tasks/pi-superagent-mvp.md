# pi-superagent MVP

Objective: a Python service that ports dsh-superagent's ideas onto the Pi agent harness: it takes explicit GitHub requests, runs one Pi worker per Ticket, and delivers replies and PRs.
Branch: main (new repo, no commits yet). Delivery: ask-on-risk. Runner: `.venv/bin/python -m unittest discover -s tests -t .` (stdlib unittest).

## Specs

- S1 (L1) "I want to use python to create my own super-agent can use in pi agent harness". Python package `superagent`, Python >= 3.11, stdlib-first.
- S2 (L2 Sources) "GitHub only (Recommended)": poll GitHub every `poll_seconds` (default 60) for issues, issue comments and PR review comments in one configured repository. Detect requests by notifications plus per-item comment reads with a cursor that steps back 5 s; Trigger ids are deterministic (`github-comment|<id>|<updated_at>`, `github-issue|<number>`), so overlap never duplicates. Skip the agent's own comments.
- S3 (L2 Identity) "Separate bot account (Recommended)": the service comments and opens PRs as the configured `agent_login`, using a token read from an environment variable named in config. Replies carry a hidden `<!-- superagent:<msg-id> -->` marker and are skipped if already posted.
- S4 Policy (explicit-only MVP): a human on `allowed` who @-mentions `agent_login` creates a Ticket (explicit mandate). `@agent stop` from an allowed human stops the Ticket on that thread. Any human comment on a thread with a live Ticket is delivered to that Ticket as context (no new authority). Bots and the agent itself are ignored.
- S5 (L2 Model) "Claude via API key (Recommended)": workers run `pi --mode rpc` with explicit `--provider`/`--model` from config (default `anthropic` / `claude-sonnet-5-5`), never the user's Pi defaults, and without the user's extensions, skills, prompt templates and context files (`-ne -ns -np -nc`) except the super-agent's own worker skill.
- S6 (L2 Safety) "Worktree + limited tools (Recommended)": each Ticket gets a git worktree on branch `agent/<name>` under `work_dir`, created from a local `checkout` of the repo. Pi gets only the configured tool allow-list. The worker environment never contains the GitHub token or other configured secrets.
- S7 Worker protocol: a run is finished only at the RPC `agent_settled` event; an assistant `message_end` with `stopReason: "error"` is a failed run, not a finished one. Extension UI dialogs are answered `cancelled` so a worker can never block. The worker reports through a `superagent-report` CLI (status `progress|waiting|ready|blocked|failed|dropped`, summary, optional question) that posts to the service over localhost with a per-Ticket token.
- S8 Delivery: on `ready`, the service pushes the branch with its own token and opens (or reuses) a PR, then comments the link on the request thread. On `waiting`, it posts the question; a human reply on the thread resumes the same Pi session. The Ticket ends when its PR is merged or closed, or when stopped.
- S9 Durability: SQLite stores Triggers, Tickets, Inputs, and an effect queue (reply, launch, deliver) with per-(kind,key) idempotency and backoff from 5 s doubling to 300 s. After a restart, running Assignments end as "host restarted" and resume with a recovery note.
- S10 Operator surface: CLI `superagent run`, `superagent status`, `superagent tickets`, `superagent stop <ticket>`, `superagent retry <ticket>`. Panel: see S11.
- S11 (L9) "can you build web panel?": a local Streamlit panel (`superagent panel [--port 8742]`, 127.0.0.1 only, optional extra `panel`) following dsh-superagent's principle that the panel shows only what needs a person. Tabs Overview (person-needed Tickets first with thread link, question/summary and Stop/Retry; 24 h counts, running workers vs `max_workers`, failing effects, last poll), Tickets (filter, search, detail), Triggers (decision per Trigger, filter by decision), Settings (read-only, token set yes/no only). Reads the store through Store methods only; Stop/Retry reuse the CLI's request function. Never shows a token or environment values. Missing streamlit exits 2 with `install the panel extra: pip install -e ".[panel]"`; a busy port is refused in one line.

- S12 (L12 "Multiple repos") One service watches a list of repositories. Config accepts `[[repos]]` tables (`name` owner/name, `checkout`, optional `base_branch`, `test_command`, `test_timeout`); the existing single `repo` + `checkout` form keeps working unchanged. Notifications are filtered to the configured repos; every Ticket records its repo; worktrees live under `<work_dir>/<owner>__<name>/<ticket-name>`; CLI and panel show the repo. One bot token covers all configured repos.
- S13 (L12 "Enforced tests") When a worker reports `ready` and the repo has a `test_command`, the service runs it in the worktree with the worker's sanitized environment (never the token) and a timeout (default 900 s). Pass: deliver, and the PR body states the command and that it passed. Fail: no PR; the failure output tail goes back to the same Pi session asking it to fix and report ready again; after `max_test_retries` (default 2) failed fixes the Ticket is reported `blocked` honestly. No `test_command`: delivery as before, PR body says no test command is configured.
- S14 (L12 Cross-repo "One ticket, many PRs (Recommended)") A request that names other configured repos (`owner/name` in its text, or several `--repo` on a local request) gets one Ticket with one worktree per repo inside one ticket folder; the worker's cwd is that folder and its first message lists each repo and path. On `ready`, each repo with new commits is tested (S13) and gets its own PR on its own `agent/<name>` branch; each PR body links the other PRs; one reply lists them all. The Ticket ends when none of its PRs is open: outcome `merged` if all merged, otherwise `closed`. Only configured repos can be named.
- S15 (L12 "Pi command") A local request source: `superagent ask [--repo R ...] TEXT` creates an explicit request from the local operator (thread `local:<id>`), `superagent show TICKET` prints its conversation (acks, questions, reports, PR links), `superagent answer TICKET TEXT` adds an input and resumes the worker, and stop/retry/tickets work as for GitHub Tickets. Replies for local Tickets go to a local outbox shown by `show` and the panel instead of GitHub. Pi integration: `superagent pi-install` installs a `superagent` Pi skill and a `/superagent` prompt template into the user's Pi agent dir (`--uninstall` removes them), so a Pi chat can create Tickets, check status and answer questions through those commands.

- S16 (L15 "Add Windows support + doc (Recommended)") Native Windows (no WSL): `superagent` installs and runs with the same features. test_command runs through cmd.exe in a new process group and a timeout kills the whole process tree; workers cannot fall back on stored git credentials or prompts; `superagent run` stops cleanly on Ctrl+C; `superagent panel` stops cleanly; the service's hardened git commands (hooks off, no global/system config, fresh push repo) work with Git for Windows. The GitHub test run includes a Windows job. README gets a native Windows install guide (cmd and PowerShell). POSIX behaviour is unchanged.

- S17 (L17 "can we see agent worker process log in the panel?") The panel's ticket detail shows a worker log: (a) the ticket's Pi session as a timeline (prompts sent, assistant text, tool calls with their arguments, tool results trimmed, errors and stop reasons, timestamps), newest activity visible without scrolling the whole page, refreshed with the panel; (b) the service's log lines for that ticket (launch, tests, delivery, reports), which `superagent run` also writes to a rotating log file in the state dir. Read-only; strings that look like tokens (GitHub, Anthropic/OpenAI keys) are masked before display; a missing or still-empty session says so.
